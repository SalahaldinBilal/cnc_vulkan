# Vulkan Backend

Our own implementation of the D3D8 device, drawing with Vulkan 1.3, and the game's only renderer. The code is in `crates/d3d8/src/vk/`.

## How the game reaches it

- `Direct3DCreate8` still creates the system IDirect3D8 and wraps it in ours (`direct3d.rs`). Adapter, mode, format and caps queries go to the system one, so the game sees the same adapter list and caps as on D3D8 and takes the same code paths.
- Our `CreateDevice` makes the Vulkan device (`vk/device.rs`) instead of a D3D8 one. The window is arranged with the same code as the D3D8 path (`native::prepare`, `window::apply`).
- Device caps come from the system D3D8 unchanged. They report ps.1.4 on modern drivers, but the game only ever creates ps.1.1 shaders (13 of them, all at startup).
- Unless the game passes `D3DCREATE_FPU_PRESERVE` (it doesn't, see `dx8wrapper.cpp`), D3D8 sets the x87 unit to single precision, round to nearest, all exceptions masked when the device is created. We do the same. The game's math depends on it, replays and multiplayer included.

## Requirements

Vulkan 1.3 with dynamic rendering, BC textures and clip distances, on a GPU that can present to the game window. The GPU is matched to the D3D adapter by vendor and device id. If Vulkan can't start, CreateDevice shows a message box with the reason and fails.

## Design

- **One command buffer per frame**, recorded in the game's call order. Render passes (dynamic rendering) start lazily on the first draw or clear and end when something has to happen outside a pass: an upload, a copy, a render target change, Present.
- **Images stay in one layout for their whole life** (`GpuImage::layout`), so nothing tracks layouts. Most are GENERAL, with a full memory barrier between rendering and transfers. Multisampled targets (the 3D world's color and depth with MSAA) are created attachment-only, in COLOR_ATTACHMENT_OPTIMAL or DEPTH_STENCIL_ATTACHMENT_OPTIMAL, and only ever touched by render passes: cleared by a pass with CLEAR loads, drawn into, and resolved by empty passes with resolve attachments (color averaged, depth and stencil from sample 0) into GENERAL single sampled images. Their depth is never sampled: `after_opaque` resolves it into the single sampled depth and copies from that. This is so AMD can keep its color and depth compression on the 8x images, which a GENERAL layout and transfer usage may prevent.
- **A second command buffer per frame runs first** and holds work nothing earlier depends on: the initial layout of new images and the first upload of textures no draw has used yet. Loading screens create thousands of textures, and this keeps them from breaking render passes.
- **Two frames in flight.** Objects the game releases are destroyed once the GPU has finished every submission that could use them (`context::retire`).
- **Dynamic state** covers viewport, scissor, cull mode, depth test, write and compare, stencil, depth bias and topology. Where the driver has `VK_EXT_extended_dynamic_state3` and `VK_EXT_vertex_input_dynamic_state` (AMD does), blending, color write mask, fill mode and the whole vertex layout are dynamic too. Pipelines then only differ by shader pair, primitive class and whether a depth buffer is bound.
- **Pipelines are built ahead.** With the dynamic state above, device creation builds the fixed function pair (with and without depth), and every CreateVertexShader and CreatePixelShader builds its pairs, all in parallel threads. The game creates all its shaders at startup, so nothing is compiled during play. Any pipeline that still has to be built at a draw (lines, points) is logged as "built during play". Without the extensions, pipelines are built on first use, keyed by blending and vertex layout as well.
- **The pipeline cache is saved** to `%LOCALAPPDATA%\cnc-vulkan\zh\vulkan-pipelines.bin` after every build and loaded at start.
- Measured: one pipeline with the fixed function pixel shader took 1 second to build when the 8 texture stages were unrolled, about 360 ms once they became a loop bounded by a uniform (so the compiler can't unroll it). That was the cause of one-time freezes in play.
- **Stats** every 5 seconds in the log (`vulkan per frame:`): draws, render passes, buffer locks, renames and bytes written, texture uploads (and how many of them were of textures a draw had already used, so changed by the game after drawing with them), uniform bytes, read-backs, new pipelines and their build time, time waiting for the GPU and in Present. A `game thread per frame:` line splits the game thread's frame into waits for the renderer thread (calls that need an answer, and at Present), the frame cap after Present, and the rest, which is the game itself. A `renderer thread per frame:` line gives the renderer thread's busy time with preparing draws (texture uploads shown inside it), buffer writes, texture creation, the 3D world's extra passes and handing the frame to the presenter. The first 20 kinds of texture the game changes after drawing with them are logged once each (`texture 64x64 A8R8G8B8 changed after a draw used it`).
- **Uniform blocks** are rebuilt on a render state change only for the states they read (`set_render_state`): lighting, normalize normals, local viewer, specular, color vertex, the four material sources, ambient and ZBIAS for the vertex block, alpha test, texture factor, shade mode and specular for the pixel block. Blend, depth, cull, stencil, color write and fill mode are read at each draw. Before, every state change rebuilt both, and busy frames uploaded about 5 MB of uniforms.
- **A draw only records what changed.** The device remembers what the command buffer has bound (`Bound`): pipeline, each piece of dynamic state, vertex layout and strides, each vertex buffer with its offset, descriptor set with its offsets. A new command buffer or a fullscreen pass (`Pass::draw`, which binds its own pipeline and leaves the rest undefined) bumps `Renderer::binds` and the device forgets all of it. Before, every draw recorded about 20 state commands, rebuilt the vertex layout with five heap allocations, and bound everything again, about 2 µs of CPU per draw (1.6 ms for 800 draws, 6 ms for 2,455).
- **Uniforms already written are reused.** A rebuilt block that matches the last one written this frame byte for byte keeps the old slice instead of taking new ring space.
- **The object matrices are push constants.** The fixed function vertex block is about 1.7 KB (projection, 8 texture matrices, 8 lights, material). Profiling Generals zoomed out over a big base (2,000 to 3,000 draws per frame) found about 10% of the main thread copying, comparing and clearing it: the world matrix changes on nearly every draw, so the whole block was rebuilt, compared with the last one, written to the ring and copied again for the next comparison. World times view and its normal matrix (128 bytes, `state::object_matrices`) now go in a vertex push constant range of the shared pipeline layout (`var<immediate>` in WGSL, naga's `Capabilities::IMMEDIATES`), pushed when they differ from what the command buffer has (`Bound::object`). A world change no longer touches the block, and the setters only mark it dirty on a real change: SetTransform, SetMaterial, SetLight (only for an enabled light) and LightEnable compare first, since the game sets the same lights and material for every mesh. A vertex layout change only rebuilds it when the `VertexInfo` the block reads differs. Likewise SetTexture only rebuilds the pixel block when a stage gains or loses a texture, the only thing the block reads from textures (the new texture itself goes in the descriptor set). The translated game shaders don't use the range.
- **Draw culling.** A fixed function draw with plain XYZ positions (no RHW, no blend weights) from a vertex buffer that isn't dynamic is skipped when the box around all of the buffer's positions, carried by world times view times projection, lies wholly outside one clip plane (with 1% slack for the half pixel shift and ZBIAS). Such a draw can't produce a fragment, so skipping it can't change the image. The box is computed from the buffer's CPU copy on the first draw after a write and kept per stride (`BufferData::bounds`). Dynamic buffers are rewritten every frame and drawn in parts, so they're never culled. Buffers shared by many meshes get a big box and rarely cull, which is only a missed saving. It runs after `sync_scene`, so 3D world detection sees the same draws as before. The `vulkan per frame` line counts culled draws. Aimed at the terrain, which draws every tile of the map in every pass when the whole terrain is loaded (zoom out past 100%, see [camera.md](camera.md)).
- **Timers use the timestamp counter.** The `cpu per frame` timers run on every draw and buffer lock. `Instant` on 32-bit costs a QueryPerformanceCounter call and 64-bit divisions, about 5% of the main thread in that profile, so `stats::Timer` reads `rdtsc` and the report converts ticks with the rate measured over the 5 seconds.
- **Descriptor sets are kept across frames** by their contents (uniform buffers, image views, samplers, depth copy), one cache and set of pools per frame in flight, since each frame's uniforms live in that frame's ring buffers. A combination seen before reuses its set without allocating or writing 19 descriptors. Before, the cache was cleared and the pools reset every frame, so every combination was written again each frame, and the driver time under DrawIndexedPrimitive was mostly that. A frame's cache is dropped (and its pools reset) when its command buffer starts, which waited for its last submission, if any image was destroyed since it was last checked (`context::images_destroyed`, since a set may name its view) or it holds more than 8192 sets. Image views can't be reused for another image within a frame: released images are destroyed or recycled only after the GPU finishes the frames that could use them. Recycled texture images keep their view, so their sets stay valid. The `vulkan per frame` line counts descriptor sets written.
- The last pipeline key is remembered in front of the pipeline map, and the sampler, vertex format, pipeline and descriptor set maps use FxHash instead of SipHash.
- **Who creates textures.** Busy stretches in the main menu loop had the game create 60 to 70 textures per frame with 11 to 12 ms of the game's own time. Each CreateTexture now records the game's call chain, found by scanning the stack for return addresses into game.dat's code that follow a call instruction (`game::stack_callers`, a heuristic). When 100 or more textures were created in a 5 second period, the log names the four busiest chains (`70 textures created from 0x... < 0x... (last 128x128 A8R8G8B8)`). The first version took every such value: past D3DXCreateTexture (`0x007dbcc4`) and `_Create_DX8_Texture` (`0x00838a20`) the chains were stale return addresses of the memory allocator left in the stack. Now a direct call only counts when its target is at most 16 KB before the previous return address, and `call [abs32]` (how the game calls Windows, here the allocator's critical section calls) never counts. Even before that the chains named the gadget text draw, see [text.md](text.md). That run: about 70 64x64 A4R4G4B4 textures per frame while the options menu was open, 11 ms of the game's own time per frame, and about one per frame in the main menu.
- Results of the first run with these changes: 2,000 to 3,000 draws per frame take 0.8 to 1.5 ms to prepare, about 0.4 µs per draw (was 2 µs), and uniforms went from about 3.7 MB to 1.1 to 1.3 MB per frame.

## Fixed function

One vertex shader and one fragment shader (`vk/shader/ff.rs`, WGSL compiled with naga) implement the whole fixed function pipeline, driven by uniforms: transform, lighting (directional, point, spot, up to 8 lights, material sources), texture coordinate generation (camera space position, normal, reflection vector), texture transforms, and all 26 texture stage ops with their arguments, temp register and bump mapping. Alpha test runs at the end of every fragment shader.

Details that match D3D:

- D3D's y axis points up and pixel centers sit at integer coordinates. Clip space positions get flipped and moved half a pixel (`to_vulkan`). Pretransformed (XYZRHW) vertices are moved half a pixel too.
- Front faces are clockwise on screen, as in D3D.
- 2D texture coordinates enter the texture matrix as (u, v, 1, 0). WW3D's UV scroll puts the offset in `_31`/`_32` (`mapper.cpp`), which confirms it.
- A material source that names a vertex color the vertex doesn't have falls back to the material color.
- A stage op that reads the texture of a stage with no texture passes the current color through (Wine's `is_invalid_op`, which matches Windows). Stage 0's default alpha op reads the texture, so this decides the alpha of untextured draws.
- D3DCOLOR vertex data is fetched as RGBA and swizzled in the shader.
- Attributes a vertex format doesn't have come from a dummy binding with stride 0: zero, opaque white diffuse, transparent black specular.
- Render targets without alpha (X8R8G8B8, the back buffer) read destination alpha as 1, so `DESTALPHA` becomes `ONE` and `INVDESTALPHA` becomes `ZERO`.
- `ZBIAS` steps are 0.000005 of the depth range, the conversion D3D9's `DEPTHBIAS` uses for D3D8 games. Applied in the vertex shader as a clip z offset (see Reversed depth).
- User clip planes (`SetClipPlane`, `CLIPPLANEENABLE`), up to 6, in world space as D3D's fixed function pipeline takes them. The vertex block carries them moved into view space (`state::clip_planes`), and the shader writes them as Vulkan clip distances, so they clip whatever pixel shader runs. Pretransformed vertices aren't clipped. The game's vertex shaders write 1 (never clipped), and the log says so once if planes are on during such a draw. The game itself never enables them. We use them to clip roads to the terrain ([camera.md](camera.md)), through `device::with_clip_planes`, which sets them on the device the game draws with and puts the game's back after. The GPU test clips a quad drawn with a moved view.

## Reversed depth

Depth runs from 1 at the near plane to 0 at the far plane, in a float depth buffer. Floats are densest near 0, which is where distant geometry lands, so precision becomes relative to distance instead of collapsing far away. With the game's near plane of 10, the old D3D layout gave a depth error of about z² × 6e-8 / 10 world units (0.2 at z = 6000, where a terrain cell is 10), reversed gives about z × 1e-7. This matters for zooming the camera out further.

- Fixed function: the projection uniform is the game's projection with its z column replaced by w minus z (`Matrix::reversed_depth`), so the matrix itself produces the reversed value. The game's own matrix is kept for GetTransform.
- The game's vertex shaders: we don't know which constants hold their projection, so `oPos.z` becomes `oPos.w - oPos.z` after the shader. Correct, with the old precision for those draws.
- Pretransformed vertices: `1 - z`. Clears: `1 - Z`. Viewport depth range: `1 - MaxZ` to `1 - MinZ`.
- Compare functions trade less and greater (`reversed_compare`). Stencil is unaffected.
- `ZBIAS` used to be a hardware depth bias in 24-bit steps. A float depth buffer scales a hardware bias by the depth value, so the bias is now added to clip z in the vertex shader (`depth.z` in the vertex uniforms), which gives the same offset as before.
- The GPU test draws projected quads in both orders and a coplanar quad with and without ZBIAS.

Not implemented, never seen in the trace: fog, vertex blending, point sprites, cube and volume textures, palettes, additional swap chains, patches. Each logs once if the game ever uses it.

## Texture filtering

Samplers are made from the stage's filter, address, bias, LOD and anisotropy state, and cached by it. The "Texture filtering" setting (Options.ini `CncVulkanAnisotropy`, default 16) changes 3D draws only: a stage with a linear or anisotropic min filter and any mip filter gets trilinear filtering and the chosen anisotropy (or the game's own, if higher). Pretransformed (XYZRHW) draws are the UI and keep the game's filtering. The game's vertex shaders draw 3D and count as 3D. The setting applies at once: the next draw rebuilds its descriptor set when the level for its kind of draw changes.

## The game's shaders

`vk/shader/sm1.rs` translates vs.1.x and ps.1.0 to 1.3 bytecode to WGSL. It covers every opcode the game's 14 shaders use (mov, add, mul, mad, lrp, dp3, m4x4, tex, texbem, relative constant addressing) and the rest of the 1.x arithmetic and texture set except the 3x3 cube map lookups. ps.1.4 is not supported. The test in `vk/tests.rs` translates and compiles all 14 shaders from the trace.

## Resources

- **Texture images are recycled.** A released texture's image goes into a pool (up to 512) keyed by format, size, levels and alpha swizzle, and the next texture of that kind takes it once the GPU is done with it. The game creates and releases dozens of textures per frame in some scenes (66 per frame in a stretch of the main menu's background battle, nearly all drawn once). A fresh image's contents are undefined too, so a recycled one behaves the same. `cpu per frame` shows how many textures were created and how many got a recycled image.
- **16-bit texel conversion** goes through a 65536-entry table per format (R5G6B5, X1R5G5B5, A1R5G5B5, A4R4G4B4, X4R4G4B4), built the first time it's needed, instead of shifts and divisions per pixel. In the stretch above, uploads took 2.7 ms per frame for 1.4 MB.
- **Textures** keep every level in the game's format in memory, like D3D8's managed pool. Locks go to that copy. Changed levels are converted (16-bit and other small formats to B8G8R8A8, DXT copied as BC1 to 3) and uploaded right before the next draw that uses them.
- **Render targets** (textures with `D3DUSAGE_RENDERTARGET`, the back buffer, `CreateRenderTarget`) live only on the GPU, always as B8G8R8A8. Locking one reads it back and waits for the GPU.
- **Image surfaces** live only in memory. `CopyRects` copies between any two surfaces of the same format, reading back or uploading as needed.
- **Static vertex and index buffers** keep a copy in normal memory, which the game locks. Unlock writes the locked range into the GPU's copy. An unlock that would change data the GPU still has to read moves the buffer to a fresh GPU copy first and writes the whole buffer. `NOOVERWRITE` writes in place, as the game promises not to touch data in use. The CPU never reads GPU memory: it is write-combined, and reading 1 MB of it took 46 ms against 0.16 ms to write it. The first version copied buffers by reading the old GPU copy and ran the menu at 18 fps.
- **Dynamic buffers** (`D3DUSAGE_DYNAMIC`) have no separate CPU copy: Lock returns a pointer into the GPU's copy and the game writes straight into it, as on D3D8. Their copies live in cached, coherent system memory (`Context::system_buffer`, gpu-allocator's `GpuToCpu`), which the GPU reads over the bus, not in the CPU-visible video memory the other host buffers use (`CpuToGpu`, which picks device-local memory when the BAR exposes it). The game fills them field by field, and in write-combined video memory every locked instruction after such writes waited for them to reach the GPU: the first version put them there, and the sorting renderer's copy loop (`0x00808f20` in Generals) went from under 0.5% to 5 to 6% of the main thread, the shadow decal and volume fills grew too, and our own Lock and the blend tile cache showed 3 to 4% each, stalled on their atomics. A `DISCARD` lock of one the GPU still reads moves it to a fresh copy first. `NOOVERWRITE` and read-only locks use the current one. A plain lock (no DISCARD or NOOVERWRITE) of one the GPU still reads needs its current contents, which only the GPU's write-combined copy holds. The buffer then copies that once into a CPU copy and is handled like a static buffer from then on (the log counts these as buffers switched to a CPU copy). The first version instead read the GPU's copy into a fresh one on every such lock. In Generals, a terrain sub-renderer (`0x0074baa0`, see [performance.md](performance.md)) gets one every frame, and reading its buffer took about 30 ms a frame, which dropped a match to 25 fps. Before, every dynamic buffer write was copied twice, once by the game into our copy and once by us into the GPU's, 4.8 to 5.5 MB per frame in a Generals match and about 7% of the main thread. The `vulkan per frame` line shows bytes copied to buffers and bytes locked for direct writes apart. The GPU test checks every kind of lock against draws recorded before it.
- **Depth** is D32S8 (32-bit float depth), D24S8 only on a GPU without it. See Reversed depth.

## Present

The game draws into its own back buffer image. Present draws it into the swapchain with a fullscreen triangle (`vk/post.rs`): texel for texel when the sizes match, filtered when the window's client area differs. The same pass applies the gamma ramp.

**Shadow brightness** (the options menu's "Shadow brightness", [options-menu.md](options-menu.md)) is a black level lift after the ramp, per channel: `out = lift + (1 - lift) × in`, with the lift a fraction of full scale. Fog of war, shroud and night maps multiply the ground down to a few code values above 0, and some monitors show those as black (a low black level setting, HDR left on in Windows, a limited/full RGB range mismatch), so the ground under the fog disappears there. The game's Brightness slider is a gamma curve that lifts midtones with the darks, and Generals never sets a gamma ramp at all. The lift turns black into a very dark gray: a monitor that crushes the lowest levels still shows it as black, the levels just above become visible, white stays white. It covers the whole picture, menus and cursor included, as a monitor setting would.

- The swapchain is B8G8R8A8_UNORM (R8G8B8A8_UNORM next), where the shader's output is the code value. Only a surface offering neither falls back to its first format. If that's an sRGB one, the lift is done in encoded space (encode, lift, decode) so a percent means the same code values.
- The values reach the presenter through `swapchain.rs` (`set_shadow_brightness`, `preview_shadow_brightness`, `show_calibration`), read when the game thread hands a frame over (`Job`). A preview, while the options menu is open, replaces the saved value until it's cleared.
- **The calibration pattern** is drawn by the same pass while the Graphics tab of our page is open. The page gives an area in back buffer pixels, scaled to the swapchain when the sizes differ, and `post::calibration_pattern` fits the largest pattern in it: a black box 41 by 6 units with a gray outline (64 of 255, a fifth of a unit wide), and inside it a row of eight squares 4 units wide, one unit apart, at input levels 1, 2, 3, 4, 6, 8, 12 and 16 from left to right. Its pixels replace the back buffer's before the ramp and the lift, so it shows exactly what the setting does to dark game pixels.
- The first pattern only went up to level 6. On a monitor that crushes the lowest levels all its squares were black at Off, so nothing told the player where the pattern was or that it worked. The brighter squares show on almost any monitor, and raising the lift brings the fainter ones in one by one. It also sat in the strip right of the 4:3 area, where the main menu's buttons (anchored to the right edge) reach, and it covered them.
- The GPU test runs the pass into the back buffer (`device::present_pass_for_test`) and checks a lifted black, an unchanged white and the pattern's levels.

**A presenter thread does the presenting** (`vk/swapchain.rs`). At Present the game thread only ends the frame's command buffers (`Renderer::finish`, which also counts them as submitted for resource lifetimes), reserves room for the present pass's uniforms in the frame's ring, and hands the frame over. The presenter acquires the swapchain image, records the copy and the layout changes into its own command buffer (one per frame in flight, each in its own pool, with a full barrier first so the frame's writes to the back buffer are visible), submits the frame's buffers and that one together with the frame's fence, and presents. Before, the acquire, the submit and the present (driver, win32u and ntdll time, about 6% of the main thread in a Generals match) ran on the game thread.

- The game thread stays at most one frame ahead: handing over a frame waits until the presenter has finished the previous one. So when the game thread moves on and waits for the other frame in flight's fence, that frame has been submitted.
- Every use of the queue (submit, present, wait idle) holds `context::QUEUE`. Anything that waits for the GPU on the game thread (readbacks, Reset, release: `flush_and_wait`, `wait_idle`) first waits until the presenter is idle (`swapchain::drain`), so submissions stay in order.
- The swapchain itself (`Chain`) belongs to the presenter. Recreating it (size change, Reset's stale flag) happens there, after a device wait idle.
- The `ms in present` stat is now the hand-over, including any wait for the presenter. The acquire's wait still counts as waiting.
- A panic on the presenter aborts the process like anywhere else (`panic = "abort"`), so a failure there can't leave the game waiting forever.

**Command recording is deferred too** (`vk/render.rs`). The game thread still does all D3D state handling, draw preparation, uniforms and descriptor sets, but it never calls `vkCmd*`. It appends `Cmd` records to the frame's two lists in `Renderer` (`main` and `init`, each a `Recording`). The common commands are enum variants: pipeline, dynamic state, descriptor set, push constants (an index into a side vector of fixed-size blocks), vertex and index buffers, draws. Anything rare (barriers, render pass begin and end, copies, clears, blits, resolves, the vertex input layout, post passes) is `Cmd::Other`, a boxed closure that captures only raw handles and owned data, never a reference into the device.

- `Renderer::finish` takes both lists and returns a `Submit` (command buffers, lists, fence, acquire semaphore). A non-empty init list gets a full barrier at its end. The frame counts as submitted for resource lifetimes at that point.
- Whoever submits replays: the presenter thread at Present (`Submit::record`, begin, replay, end), or the game thread in `submit` for readbacks and Reset, after `swapchain::drain`. Command buffers are begun by the replay, not in `begin_main`.
- Lifetimes need nothing new: anything released while its commands wait in a list was used by the current recording id, so it's destroyed after that submission completes, which is after the replay. Pipelines replaced by the post passes (`set_target`) go through the same garbage list instead of being destroyed at once.
- A post pass draw (`post.rs`) is split in two: `write_set` writes its descriptor set on the game thread, and `PassDraw` (from `commands`) holds the handles the recorded closure needs. The presenter uses the same pieces for the present pass.
- Descriptor sets are only written when they're new (they're cached, see Resources), so no set changes while a list that uses it waits.
- The vulkan log line's `ms recording command buffers off the game thread` is the replay time, almost all of it on the presenter.
- The vertex input layout (`vkCmdSetVertexInputEXT`) is its own command, `Cmd::VertexInput(Arc<VertexInput>)`, cached on the device per layout and strides, and turned into stack arrays at replay. As a boxed closure it cost several heap allocations per layout change on both threads (about 2% of the main thread, `ntdll` under DrawIndexedPrimitive).
- A fixed function draw's descriptor set only holds the stages it samples, up to the first one with COLOROP disabled (`state::active_stages`, the same count the pixel uniforms carry). The other stages get the white image and stage 0's sampler, so textures left bound in unused stages don't make sets of their own, and the key needs one sampler lookup per used stage, not eight. Each stage also remembers its last sampler key and sampler. Programmable pixel shaders get all 8 stages.
- `Recording::take` hands the lists over and starts the next frame's with the same capacity, so they don't regrow every frame (`RawVec::finish_grow` was about 2% under our code).
- Uniform blocks (1.7 KB vertex, 0.8 KB pixel) are compared with the last ones written, and transforms, lights and materials with the stored ones, through `state::bytes_equal`, which has no early exit so it compiles to wide compares instead of a memcmp call. The vulkan line counts the blocks built per frame (`vertex and pixel blocks built`), each one a block that was rebuilt because its state changed.

**A renderer thread runs the device** (`vk/worker.rs`). The game thread only queues its D3D calls. Everything behind the device (its state, `Renderer`, pipelines, descriptor sets, the scene target, buffer and texture data) is only touched on the renderer thread, in the order of the game's calls, so the existing single-threaded code (`Rc`, `RefCell`, the thread-local image pool) runs there unchanged.

- **Queue.** Closures are stored inline in a batch of 8-byte words (a header with the call and the entry's length, then the closure's bytes), no allocation per command. `post_bytes` stores a byte slice after the closure, for data the call needs a copy of (unlocked ranges). Each producing thread has its own batch, handed to the renderer thread every 4,096 words, before any `run`, and at Present. Commands queued on the renderer thread run inline.
- **`run`** waits for a call to finish on the renderer thread after everything queued before it. Every vtable entry not otherwise handled points at a wrapper in an `on_worker` module at the end of `device.rs` and `texture.rs` that does that (`run_as`, counted by name).
- **Queued without waiting** (`device.rs`, `on_worker`): render states, texture stage states, transforms, viewport, material, lights, clip planes and status, palette, textures, streams, indices, shaders and their constants, render targets, Clear, CopyRects and the four draw calls. Zero Hour calls CopyRects about once a frame, and as a waiting call it held the game thread about 5 ms each time. A `Front` (allocated at creation, only touched on the game thread) mirrors what Get* calls return, so getters never wait. Objects a queued call names get an AddRef when queued and a Release after the call ran (`Held`). Reset and ApplyStateBlock wait, then copy the device's state into `Front` again (`refresh_front`). Shader creation and deletion wait and keep `Front`'s list of live shaders.
- **Scene flags.** `scene::in_scene`, `opaque_done` and `in_sorted` are sent along (`send_scene`) when they changed, before draws, clears and Present, into `Device::scene_flags`, which `sync_scene` and soft particles read instead of the globals.
- **Present** is queued (`worker::present`) and the game thread waits only while the frame before is still unfinished on the renderer thread, so it runs at most one frame ahead. Fog, Discord, stats, `frame::on_present` and the frame cap stay on the game thread.
- **Reference counts** of buffers, textures and surfaces are atomic and change on the game thread directly. The last Release queues the destruction. The device's own count stays on the renderer thread. Device release restores the display mode and releases our IDirect3D8 on the game thread: a mode change sends messages to the game's window while the game thread would be waiting.
- **The game thread's copies are kept only where they're used.** The first version kept a copy of every buffer and every texture level on the game thread, on top of the renderer side's, and Zero Hour ran out of address space loading a map (a fast fail, exception 0xC0000409 in `rust_oom`, nothing in our log; Windows' Application log named it). Now a copy is made at a resource's (or level's) first lock and dropped after its first unlock, since most are written once at load. From the second lock on it's kept. A later lock that may read (anything but DISCARD or NOOVERWRITE on a buffer, any texture lock) first fetches the contents from the renderer thread with a `run`. Batches that grew past four times their usual size carrying such data aren't kept for reuse. The GPU test locks a buffer and a texture a second time and checks they read back what was written.
- **Buffer locks** are answered on the game thread from a copy of the buffer's contents in `Buffer::front`. Unlock queues the written range (`post_bytes`), and the renderer thread replays it as lock, copy, unlock on `BufferData`, so renames and the CPU copy logic stay as they were.
- **Texture locks** the same: `Texture::front` holds every level of a lockable texture, LockRect on the texture or one of its level surfaces points into it, UnlockRect queues the written rows, which the renderer thread copies into its own copy and marks for upload. Anything that changes a texture's levels on the renderer thread otherwise (CopyRects, UpdateTexture, our radar code) goes through `mark_dirty`, which sets `front_stale`, and the game thread fetches the levels again before its next lock. Render targets and memory surfaces wait for the renderer thread.
- **Reset** waits for the renderer thread for its two halves and arranges the window on the game thread in between: window calls from the renderer thread would wait for the game thread's message loop while it waits for them.
- **Our modules** (radar, radar layers, radar map, fog) read the game's memory on the game thread and do their texture work with `run` or `post`.
- Getters that only read what never changes after creation (caps, display mode, descriptions, private data, priority, level counts and surfaces) answer on the game thread.
- Image ids are a global atomic, they were thread-local.
- The log shows the split: `game thread per frame` (waits on calls to the renderer thread, at Present, the frame cap, the rest), `renderer thread per frame` (busy time, preparing draws, buffer writes, texture creation, 3D world passes, handing the frame to the presenter), and `calls that waited for the renderer thread, per frame` by method.

**GPU timestamps** (`[debug] timers`). Each frame slot has a timestamp query pool (64 queries), reset at the start of the slot's recording. `Renderer::mark(section)` writes a timestamp (bottom of pipe) after everything recorded so far, and the section runs until the next mark. Marks: the frame's start, the world's start, the end of its opaque geometry (depth copy and ambient occlusion), then shadows and other translucent work, the sorting renderer's flush (sorted translucent polygons and particles, preceded by the resolve to single sampling, counted with the resolves), the world's close (resolve, scaling, FXAA), then the interface until `finish`. They're read back without waiting once the slot's fence has signaled, and logged as `gpu per frame`. A readback or Reset in the middle of a frame closes the marks there and starts again in the same section. The present pass on the presenter isn't covered.

The brightness setting reaches us as SetGammaRamp. WW3D's `DX8Wrapper::Set_Gamma` builds one ramp for all three channels and calls the device's SetGammaRamp whenever the caps report `D3DCAPS2_FULLSCREENGAMMA` (modern drivers do), and GDI's `SetDeviceGammaRamp` on the desktop otherwise (EA source). D3D8 ignores the ramp on a windowed device, so on borderless and windowed the setting never did anything. We apply it in every mode. D3D looks up 8-bit output values, the pass blends the two nearest entries for values in between. Each call logs the ramp at five points.

Vsync uses FIFO, otherwise IMMEDIATE (or MAILBOX).

## Latency and pacing

- Present runs inside the client update's draw. The window messages are pumped and input is read after it returns, so anything that waits right after Present delays the next frame's input, not the frame already drawn. The frame cap (`pacing.rs`) waits there, and with vsync on too: FIFO plus a cap a few fps under the refresh rate is the usual setup for a variable refresh rate display.
- No vendor latency extension. AMD Anti-Lag 2, NVIDIA Reflex and a `VK_KHR_present_wait` fallback were used before, behind a "Low latency" setting (Options.ini `CncVulkanLowLatency`, now ignored), and removed: game commands wait for the next 30 Hz logic step anyway, the game's cursor doesn't depend on our frames, Generals is CPU-bound where they do nothing, and their sleep at the start of the frame on the game thread got in the way of moving draw preparation to another thread. How far the CPU runs ahead is bounded by our own design instead: at most two frames in flight on the GPU, and the game thread no more than a frame ahead of the presenter.
- Whether borderless gets independent flip (and so VRR) is the driver's choice for a Vulkan window. PresentMon shows it: "Hardware: Independent Flip" is good, "Composed: Copy with GPU GDI" is not.

Exclusive fullscreen (display mode `fullscreen`, the game asking for a fullscreen device) switches the monitor to the game's resolution with `ChangeDisplaySettingsEx` and covers it with the window. Losing focus restores the desktop mode and minimizes the window, gaining it back switches again (`vk/display.rs`).

## Testing

`cargo test -p d3d8 --release` runs `vk/gpu_tests.rs`, which opens a small window and drives the device through its D3D8 interface: clears, pretransformed and transformed quads, half pixel edges, textures (including DXT1), a game pixel shader, the tree vertex shader, alpha test, blending, depth, stencil, indexed buffers, every kind of dynamic buffer lock, render to texture, CopyRects, lighting, Present and Reset. Every check reads pixels back.

## Validation

`[debug] validation = true` in `cnc-vulkan.toml`, or the `CNC_VULKAN_VALIDATION` environment variable, loads `VK_LAYER_KHRONOS_validation` (`vk/validation.rs`). Warnings and errors go to our log as `vulkan validation error: ...`, each message id at most 3 times. The game and the tests are 32-bit, so the layer has to be the 32-bit one: the LunarG Vulkan SDK installs it only with its optional 32-bit components. Without it the log says the layer isn't installed and the game runs without it. With the environment variable set, the GPU test fails if the layer reported any error.
